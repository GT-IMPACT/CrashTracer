# Диагностика Mixin и ASM

## Mixin Inspector

Строить связи: **мод/JAR → Mixin config → Mixin class → target class/method → результат применения**. Сопоставлять target-классы со стектрейсом инцидента.

Нужные сведения:

- Конфигурация, класс миксина и его предполагаемый владелец.
- Целевой класс и доступные сведения о методе/точке инъекции.
- Фаза и статус применения, сообщение ошибки.
- Доказательства соответствия конфигурации исходному JAR.

Различать зарегистрированный, применённый и завершившийся ошибкой миксин. Если источник не позволяет определить статус, указывать неизвестность. Ошибка поиска точки инъекции может означать конфликт трансформаций или несовместимость target-класса; это ещё не доказательство конкретного виновника.

## Режимы

По умолчанию собирать метаданные. Экспорт bytecode, `mixin.debug.export` и подробное логирование — отдельный диагностический режим. Не выгружать все классы при обычном запуске.

Дополнительное вмешательство в Mixin processor допускается после изучения UniMixins Compat. Простых `@Inject` может быть недостаточно для полноценной истории трансформаций.

## Transformer Inspector

Собирать известные ASM-трансформеры, их принадлежность coremod/JAR и доступный порядок применения. Для диагностики `VerifyError` и конфликтов связывать трансформеры с изменёнными классами, когда есть соответствующие данные.

Регистрация трансформера не доказывает изменение конкретного класса. Историю фактических преобразований и сравнение байткода проектировать отдельно; они могут потребовать ASM-инструментирования и не входят в MVP.

В отчёте разделять наблюдаемые изменения, предположения о конфликте и отсутствующие данные. Полные дампы хранить в `evidence/` только при включённом режиме и с ограничением объёма.
