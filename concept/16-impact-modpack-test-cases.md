## Первый IMP-01: ранняя загрузка FML и исправление

В 16:00:26 клиент остановился до запуска: MixinTargetAlreadyLoadedException для
нашего forge.LoadControllerMixin. Другие coremods сборки загрузили
cpw.mods.fml.common.LoadController раньше фазы DEFAULT, в которой находился hook.
Точная инициирующая загрузку сторонняя библиотека по этому логу не установлена.
Это новая несовместимость Crash Tracer, отсутствующая в baseline.

Исправление: FML hook вынесен в отдельный mixins.crashtracer.fml.json с фазой PREINIT,
регистрируемый через manifest; в динамическом DEFAULT-списке он больше не добавляется.
Minecraft/BetterCrashes hooks остаются в прежних фазах, FML hook не отключён.

Добавлена фикстура serverSmokeScenario=early-fml: другой coremod намеренно загружает
LoadController в IEarlyMixinLoader.getMixins, до перехода к DEFAULT. До исправления
она воспроизводит тот же fatal prepare; после исправления сервер запускается,
делает 120 тиков и останавливается. Проверено с UniMixins 0.3.1 и с точной копией
release JAR UniMixins 0.3.2 из модпака. Отдельный reobf FML initialization crash
сохраняет fml-lifecycle, cause/suppressed и дедупликацию в обычный CrashReport.

Серверные проверки не заменяют повторный запуск полного клиента Prism.
Исходный лог, старый JAR и сведения об исправлении: build/modpack/IMP-01-before/;
технические прогоны: build/server-smoke-early-fml-*.log,
build/early-fml-release-verification.log, build/early-fml-final-build.log.

## Первый IMP-02: отчёт готов, выявлен дефект ограниченного снимка

В 16:18:27 создан обычный `crashtracer-client-1792070307862.txt` и один инцидент
`1792070307845-8c9cef99-93eb-4e8e-bef2-234acc097e1f` в той же сессии IMP-01.
RuntimeException, cause и suppressed сохранены; 171 modid, heap, клиентский и
серверные worlds присутствуют. Анализ завершился в 16:18:29 и определил фикстуру
с LOW по владению классом. Суммарный размер артефактов — 606935 байт.

Снимок достиг maxThreads=128 и не содержал Client thread, хотя capture выполнялся
именно на нём. MXBean не гарантирует порядок allThreadIds: выбор первых N
не гарантировал сохранение важных потоков на большой сборке. Server thread присутствовал.

Исправление сохраняет приоритет deadlocked threads, затем выбирает поток capture
и живые client/server threads из heartbeat; остаток лимита отводится прочим потокам.
Лимит касается только записи отчёта, не числа работающих JVM threads. Лимит 128
оставлен прежним. Добавлен регрессионный тест со снимком всего на два потока:
capture и переданный игровой thread обязаны попасть в него без дублей.
Сборка и 31 тест на Java 8 проходят. После подтверждения закрытия клиента
исправленный JAR установлен в тестовую копию Prism; старый сохранён в
build/modpack/IMP-02-before/. SHA-256 установленного файла проверен.
Повтор IMP-02 нужен после запуска с исправлением.

## IMP-06 — FAIL: блокировка GregTech после servercrash

Повторный вход в 16:51:42 завис. Снимок jstack в 16:54:59 показывает новый
Server thread #471 в WAITING на ReentrantLock внутри GT_Proxy.onServerTickEvent:1094.
Client thread ждёт завершения сервера в Minecraft.func_71353_a:2176.
Watchdog самостоятельно записал STALL в 16:52:43:
`1792072363940-34775f4d-d1d4-4ccb-ac5e-5d5dde339570`, анализ — gregtech LOW.
Это не обнаруженный JVM цикл deadlock: findDeadlockedThreads не сообщает цикл.

Байткод установленного gregtech.jar подтверждает: статический TICK_LOCK берётся
на ServerTickEvent.START и освобождается на END. Фикстура бросила исключение
на START после обработчика GT; END не был выполнен. Предыдущий серверный поток
завершился, новый не может получить оставшийся lock. Это объясняет зависание
после намеренного сбоя внутри тика; обычный выход/повторный вход ещё надо проверить
после полного перезапуска JVM. Автоматически освобождать чужой lock нельзя.

IMP-05 подтверждает сохранение диагностики, но не успешное восстановление мира.
Для продолжения нужен полный перезапуск клиента, затем обычные входы/выходы
без повторного servercrash. Логи, watchdog-отчёт, jstack и байткод сохранены
в build/modpack/IMP-06-fail/.

## Первый IMP-16 — FAIL, исправление ждёт повтора Prism

В 17:37:31 и 17:37:56 запуск с experimentalTransformers/bytecodeExport оборвался
на GTNHLib MixinBlockFlowerPot: LVTGeneratorError для getDrops. Обёртки скрывали
IClassNameTransformer/ITransformer и исходные имена от Mixin/Mixingasm.
Это несовместимость экспериментального режима Tracer.

Теперь ранний bootstrap пишет DEFERRED; адаптер включается в FML preInit после
классификации оригинальных трансформеров Mixingasm. Name transformers и Mixin
proxies сохраняют identity; обычные адаптеры предоставляют Mixin исходное имя
и прямой metadata delegate. Ограничение: трансформации до preInit не трассируются;
ранний перехват ошибок через bootstrap/LaunchWrapper остаётся независимым.

## Подготовка

1. Создать копию экземпляра PrismLauncher для тестирования. Использовать копию
   развитого мира либо отдельный `CT-IMPACT-TEST`; исходный `Main 2026` не использовать
   для намеренных крашей. Нужна база с работающими механизмами, не только пустой мир.
2. Обновить BetterCrashes и выполнить IMP-00. Существующие Forgelin/UniMixins
   оставить в одном экземпляре. Во время подготовки файлы модпака агентом не менялись.
3. В тестовую копию установить **обычный release/reobf JAR** Crash Tracer и
   `crashtracer-<version>-client-smoke-fixture-reobf.jar` из build/libs.
   Dev JAR и standalone analyzer в mods не класть. Команды `/cttest` даёт фикстура.
4. Для основного прохода: enabled=true, watchdog=true, hangThresholdSeconds=60,
   watchdogCooldownSeconds=300, experimentalTransformers=false, bytecodeExport=false.
   Остальные лимиты — defaults. Config читается при запуске.
5. Подготовить одну площадку: цепочка GregTech/IC2, AE2 с хранилищем и автокрафтом,
   транспорт EnderIO/LogisticsPipes/SFM, OpenComputers и доступ к другому измерению.
   Записать состояние и контрольные количества предметов до каждого crash-теста.

**Поля прогона:** дата, версия экземпляра, JAR/SHA-256 Crash Tracer, новый JAR
BetterCrashes, Java, JVM args/heap, resource/shader packs, мир, sessionId.
Результаты записывать в [таблицу прохода](test-data/impact-dev42-results.csv):
NOT_RUN / PASS / FAIL / BLOCKED / N/A. Отсутствующий подготовленный стенд — BLOCKED;
неприменимая функция — N/A с причиной. Не отмечать такие кейсы PASS.

## Основной проход

### IMP-00 — Базовый запуск после обновления BetterCrashes · P0

**Шаги:** без Crash Tracer и фикстуры запустить обновлённую копию через Prism,
войти в тестовый мир, открыть NEI и GUI GregTech/AE2, выйти штатно.
Сохранить лог и время загрузки до меню/мира.

**Ожидание:** база сравнения работоспособна. Существующие ошибки сборки зафиксированы.
Если обновлённый BetterCrashes уже ломает запуск, сначала исправить baseline.

### IMP-01 — Запуск с трейсeром в полном наборе coremods · P0

**Шаги:** установить release Crash Tracer и reobf-фикстуру, запустить Prism.
Дойти до меню, войти в мир и проверить `/cttest` без аргументов.
Проверить LoadingScreen, Angelica/FastCraft, собственные IMPACT-миксины.

**Ожидание:** команда показывает usage; нет нового конфликта загрузки, NoSuchMethodError,
Mixin apply failure или недостающего refmap. Создана сессия трейсера.
Служебные ThisIsFake/SplashProgress не создают инциденты. Новые реальные ошибки
сравнить с IMP-00, а не считать любое появление отчёта ложным срабатыванием.

### IMP-02 — Отчёт на работающей промышленной базе · P0

**Шаги:** запустить GregTech-цепочку, AE2-автокрафт и транспорт предметов.
Открыть GUI машины, закрыть, выполнить `/cttest report`.
Дать фоновому анализу несколько секунд; проверить файлы.

**Ожидание:** обычный Minecraft report и один инцидент. Thread=Client thread;
граф: RuntimeException → IllegalArgumentException, suppressed IllegalStateException.
В контексте есть фактические версии/JAR сборки, heap, client/server worlds.
analysis.json создаётся; для искусственной ошибки владелец — тестовая фикстура
с LOW по стеку. Наличие GregTech/AE2/Angelica в окружении не делает их виновниками.

### IMP-03 — Клиентский краш на загруженной базе · P0

**Шаги:** сохранить контрольное состояние мира, включить активность стенда,
выполнить `/cttest crash`.

**Ожидание:** BetterCrashes показывает свой экран; мир сохраняется/сервер останавливается
обычным путём обработчика. Созданы обычный client crash-report и один инцидент.
Cause/suppressed целы, анализ завершён. sources.jsonl содержит bettercrashes-output,
который связан с исходным minecraft-crash-report без второго каталога инцидента.
В логе подтверждается применение CrashUtilsMixin; оно может произойти только при
первой загрузке CrashUtils, а не в начале запуска.

### IMP-04 — Восстановление и второй такой же краш · P0

**Шаги:** после IMP-03 без перезапуска JVM вернуться в меню и войти в тот же мир.
Проверить GUI/сети стенда, затем повторить `/cttest crash`.

**Ожидание:** мир снова открывается. Два разных Throwable дают два incidentId
при одном sessionId; у каждого один дополнительный BetterCrashes source.
При одинаковом стеке fingerprints совпадают. Нет цикла крашей от самого трейсера.
Состояние машин/инвентарей сравнить с сохранением; откат незавершённого игрового
тика не считать обещанной транзакционной гарантией BetterCrashes.

### IMP-05 — Краш integrated server с механизмами · P0

**Шаги:** снова войти в мир, запустить стенд и выполнить `/cttest servercrash`.

**Ожидание:** один отдельный инцидент на Server thread, трёхузловой граф сохранён,
обычный server crash-report существует. BetterCrashes на клиенте связывает тот же
отчёт без дубля. Integrated Server Crashes увеличивается; это не клиентский tick crash.

### IMP-06 — Повторные загрузки мира и смена server thread · P0

**Шаги:** после восстановления дважды войти/выйти из мира, затем открыть другой

**Ожидание:** текущий контекст соответствует открытому миру/измерению. Нет STALL

Обычные отчёты/сессии сохраняются, их очистка не затрагивает saves/config других модов.

## Что сохранять по каждому кейсу

- ID кейса, время действия, результат и точный способ воспроизведения.
- `crash-tracer/reports/<incidentId>/` целиком и соответствующий `sessions/<sessionId>/`.
- `logs/fml-client-latest.log`, `logs/latest.log`, обычный Minecraft crash-report,
  при наличии native error — оригинальный hs_err. Логи копировать до следующего запуска.
- Скриншот экрана BetterCrashes для crash/recovery и наблюдаемое состояние мира.
- Для FAIL — сравнение с baseline, версии/JAR и факт включения ASM tracing.

Реальный случайный сбой pack-мода оформлять отдельным багом: исходная ошибка,
cause/suppressed, класс/JAR, Mixin/transformer evidence. Совпадение stack frame с JAR
даёт LOW, а не доказанную первопричину. Зелёные синтетические кейсы проверяют
работу трейсера на сборке, но не доказывают способность заранее определить
виновника каждого конфликта модов.

## Критерий готовности

Все применимые P0 проходят. По P1 есть результаты или явно согласованные
BLOCKED/N/A; критические новые ошибки относительно baseline отсутствуют.
Две отдельные ошибки одного типа не сливаются в один инцидент, повторные хуки
одного Throwable не плодят каталоги. Логи и исходные отчёты доступны для проверки.
